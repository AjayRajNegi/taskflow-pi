# Task T-009: Payment webhook handler for Razorpay

## Goal
Implement a secure webhook endpoint to handle Razorpay events, particularly subscription activation and payment failures, to update subscription state.

## Requirements Covered
- From project requirements: Payment support, background job reliability for payment retries.
- From API contracts: `/payments/webhook` (POST).
- From data model: Subscriptions table.
- From security model: Payment/webhook security, input validation rules, secrets management.
- From system components: Payment service responsibility; infrastructure layer includes Razorpay abstraction.

## Acceptance Criteria
- POST `/payments/webhook` (public endpoint, but secured by signature verification):
  - Does not require authentication.
  - Validates the `X-Razorpay-Signature` header using the webhook secret.
  - Parses the JSON payload.
  - Handles relevant event types:
    - `subscription.activated`: updates subscription status to 'active', sets currentPeriodEnd.
    - `subscription.canceled`: sets status to 'canceled'.
    - `subscription.paused`: sets status to 'paused'.
    - `payment.failed`: may update subscription status to 'past_due' or trigger retry job.
    - `subscription.completed` (if applicable).
  - For each event, extracts the subscription identifier from the payload (e.g., `payload.subscription.id` which should be the Razorpay subscription ID) and maps it to our subscription record.
  - Updates the subscription record in the database with new status and relevant fields.
  - Returns 200 with `{ "status": "processed" }` on successful processing.
  - Returns 400 if payload is invalid or missing required fields.
  - Returns 401 if signature verification fails.
  - Returns 500 for unexpected errors (but logs details internally).
  - Processing is idempotent: processing the same webhook event twice should not cause inconsistencies.
- Payment service methods:
  - `verifyWebhookSignature(payload, signature)`: verifies Razorpay webhook signature.
  - `handleWebhookEvent(event)`: dispatches to appropriate handler based on event type.
- Unit and integration tests cover:
  - Signature verification with valid and invalid signatures.
  - Handling of each supported event type.
  - Idempotency: processing same event twice does not alter state incorrectly.
  - Invalid JSON payload returns 400.
  - Missing signature header returns 401.
  - Unsupported event types are logged and still return 200 (or 400? We'll return 200 but log warning).
  - Mapping from Razorpay subscription ID to our subscription record works.
  - Database updates are correct.

## Out of Scope
- Handling all possible Razorpay event types (we'll focus on subscription and payment events relevant to our use case).
- Refunds or disputes.
- Retrying failed webhooks (Razorpay handles retries; we just need to be idempotent).
- Storing raw webhook payloads for audit (optional, not required).
- Using Razorpay webhooks for other purposes (e.g., customer creation).
- Webhook endpoint security beyond signature verification (e.g., IP allowlisting) – open question.

## Important Implementation Notes
- Razorpay webhook signature verification: compute HMAC SHA256 of the payload using the webhook secret and compare with the header.
- The payload should be parsed as JSON; we verify the structure before processing.
- We must store the Razorpay subscription ID in our subscription table when creating the subscription (from T-008) to enable mapping.
- For subscription activation, update: status to 'active', currentPeriodEnd from payload.
- For subscription canceled: status to 'canceled'.
- For payment failed: we may set status to 'past_due' and trigger a background job for retry (see T-010 for notification jobs; payment retry jobs may be similar).
- Consider adding a `razorpaySubscriptionId` field to the subscriptions table for mapping.
- Handle events where the subscription ID in payload does not correspond to any of our subscriptions (log and return 200 to avoid retry loops).
- Log webhook events (without sensitive data) for monitoring.
- Return 200 only after successfully processing the event; if we cannot process (e.g., DB error), return 500 to trigger Razorpay retry.
- Ensure the endpoint does not expose any internal errors in the response body.
- Use a shared middleware for signature verification to keep the route handler clean.
