# Task T-007: File attachment service and API: upload, get metadata, delete

## Goal
Implement file attachment functionality with size limit, tenant isolation, and storage abstraction.

## Requirements Covered
- From project requirements: File attachments with 10 MB limit, tenant isolation.
- From API contracts: `/tasks/:taskId/attachments` (POST), `/attachments/:attachmentId` (GET, DELETE).
- From data model: Attachments table definition, constraints, relationships.
- From security model: File-upload security, tenant-isolation model.
- From system components: File service responsibility; storage abstraction.

## Acceptance Criteria
- POST `/tasks/:taskId/attachments` (protected):
  - Requires valid JWT.
  - Expects multipart/form-data with a file field named `file`.
  - Validates that the task exists and belongs to the authenticated user's tenant.
  - Validates file size <= 10 MB (both via middleware and before storage).
  - Optionally validates MIME type (open question; for now, we accept any but log warning for dangerous types).
  - Streams the file to the storage adapter (local filesystem in dev, Cloudflare R2 in prod).
  - Saves attachment metadata with: tenantId (from task), taskId, filename, mimeType, sizeBytes, storageKey.
  - Returns 201 with attachment metadata (id, filename, mimeType, sizeBytes, storageKey, uploadedAt, taskId).
  - Returns 400 if no file provided or file too large.
  - Returns 404 if task not found or not accessible.
  - Returns 415 if request is not multipart/form-data.
- GET `/attachments/:attachmentId` (protected):
  - Requires valid JWT.
  - Returns attachment metadata if the attachment exists and belongs to the user's tenant (via task).
  - Returns 200 with metadata.
  - Returns 404 if attachment not found or not accessible.
- DELETE `/attachments/:attachmentId` (protected):
  - Requires valid JWT.
  - Deletes the attachment file from storage and removes metadata if the attachment belongs to the user's tenant.
  - Returns 204 on success.
  - Returns 404 if attachment not found or not accessible.
- File service methods:
  - `uploadFile(taskId, userId, file)`: validates task access, streams to storage, saves metadata.
  - `getFileMetadata(attachmentId, userId)`: retrieves metadata with tenant check.
  - `deleteFile(attachmentId, userId)`: deletes from storage and metadata with tenant check.
- Storage abstraction:
  - Interface: `upload(fileStream, metadata) => Promise<{key: string}>`, `delete(key) => Promise<void>`, `getUrl(key) => Promise<string>` (if needed).
  - Implementations: LocalStorage (dev) and CloudflareR2Storage (prod).
  - The service uses the abstraction; storage choice is via configuration.

## Important Implementation Notes
- File size validation: check early in the route (middleware) to reject large files before processing.
- Streaming: use `req.file()` or equivalent to get a stream and pipe to storage adapter without buffering entire file in memory.
- Storage key generation: use UUID to avoid collisions and path traversal.
- Storage path structure: e.g., `tenants/{tenantId}/tasks/{taskId}/attachments/{uuid}` to ensure isolation and avoid naming conflicts.
- Metadata: store original filename, MIME type (from file), size in bytes.
- Timestamps: `uploadedAt` set to server time.
- Error handling: if storage upload fails, return 500 and ensure no metadata is saved (or clean up if partial).
- Deletion: delete from storage first, then metadata; if storage deletion fails, we may still delete metadata and log orphaned file (or vice versa). We'll attempt to delete both and return error if either fails.
- Security: storage keys should be unpredictable; do not guessable.
- In local development, use a temporary directory for storage.
- For Cloudflare R2, ensure proper configuration of endpoint, bucket, keys.
- Validate that the storage key is unique (UUID ensures this).
- Consider adding a file hash (e.g., SHA-256) for integrity check if needed later.
