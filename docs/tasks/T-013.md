# Task T-013: Rate limiting implementation

## Goal
Implement rate limiting to protect API endpoints from abuse and ensure fair usage.

## Requirements Covered
- From project requirements: Performance and availability considerations.
- From architecture: Rate limiting should be implemented at the infrastructure/API layer.
- From security model: Rate-limiting requirements, logging rules.
- From system components: HTTP layer responsibility includes rate limiting (implied).

## Acceptance Criteria
- Rate limiting middleware:
  - Limits requests based on IP address and/or user identity.
  - Configurable limits per endpoint or group of endpoints.
  - Returns 429 Too Many Requests when limit is exceeded.
  - Includes headers: `RateLimit-Limit`, `RateLimit-Remaining`, `RateLimit-Reset` (optional).
  - Does not block legitimate traffic under normal load.
  - Uses a storage backend (Redis) to share state across multiple API instances.
  - Excludes certain endpoints from rate limiting if needed (e.g., health check).
- Unit and integration tests cover:
  - Requests within limit are allowed.
  - Requests exceeding limit return 429.
  - Limit resets after expiration window.
  - Different IPs/users have separate limits.
  - Authenticated endpoints may have different limits than anonymous ones.
  - Rate limiting does not interfere with normal operation when under limit.
  - Headers are present in responses (if implemented).
- Configuration:
  - Environment variables to set limits (e.g., `RATE_LIMIT_AUTH_WINDOW_MS`, `RATE_LIMIT_AUTH_MAX_POINTS`).
  - Different limits for different endpoint groups (e.g., auth, file upload, payment, general).

## Files/Modules Likely to be Touched
- `src/app/middleware/rateLimit.ts` (rate limiting middleware)
- `src/infrastructure/rateLimit/` (Redis-based store or implementation)
- `src/app/routes/` (routes will apply the middleware)
- `shared/config/` (configuration service to get rate limit settings)
- Environment variables: `REDIS_URL` (shared with BullMQ), plus rate limit specific configs.

## Tests to Add or Update
- Integration tests using a real Redis instance:
  - Hit an endpoint repeatedly within limit and verify success.
  - Exceed limit and verify 429 response.
  - Wait for reset window and verify requests succeed again.
  - Test that two different IP addresses have independent limits.
  - Test authenticated vs anonymous endpoints (if we differentiate).
  - Test that rate limiting does not affect other middleware (authentication, validation).
- Unit tests for rate limiting algorithm (token bucket or fixed window).
- Test that Redis connection is reused and errors are handled gracefully (fail-open or fail-closed? We'll fail-closed: if Redis is unavailable, we may skip rate limiting or return 503; we'll decide to skip rate limiting and log error to avoid blocking legitimate traffic).

## Out of Scope
- Advanced rate limiting strategies (e.g., user-based, API key-based) – we'll start with IP-based and optionally user-based for authenticated endpoints.
- Rate limiting by HTTP method or specific parameters.
- Distributed rate limiting algorithms beyond Redis (we'll use Redis as per architecture).
- Integration with API gateway or cloud provider rate limiting features.
- Adaptive rate lifting based on system load.
- CAPTCHA or challenge mechanisms.

## Important Implementation Notes
- Choose a rate limiting algorithm: fixed window, sliding window, or token bucket. Token bucket is smooth but more complex; fixed window is simpler and sufficient for V1.
- Use Redis to store counters with expiration.
- Key format: `rate_limit:{endpoint_group}:{identifier}` where identifier is IP address or user ID.
- For authenticated endpoints, we may use user ID as identifier to prevent shared IP limits from affecting legitimate users behind NAT.
- Define endpoint groups:
  - `auth`: `/auth/register`, `/auth/login` (strict limit: 5 requests per minute per IP)
  - `file-upload`: `/tasks/:taskId/attachments` (10 per minute per user/IP)
  - `payment`: `/users/me/tenant/subscription` (5 per minute per tenant)
  - `general`: all other endpoints (100 per minute per IP)
- The middleware should be applied selectively to routes.
- If Redis is unavailable, we have two options: disable rate limiting (risk of abuse) or return 503 (risk of blocking legitimate traffic). We'll choose to disable rate limiting and log a warning, assuming that Redis is highly available in production. We'll add a circuit breaker to avoid hammering Redis.
- Log when rate limiting is triggered (for monitoring).
- Ensure that the rate limit middleware does not add significant latency.
- Test with multiple API instances to verify shared state via Redis.
- Consider exempting internal health checks or monitoring endpoints from rate limiting.
