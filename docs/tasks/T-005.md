# Task T-005: User service and API: get and update current user profile

## Goal
Implement endpoints for retrieving and updating the authenticated user's own profile.

## Requirements Covered
- From project requirements: User management is implied (users need to manage their profile).
- From API contracts: `/users/me` (GET, PATCH).
- From security model: Authorization model (users can only access their own data).
- From system components: User service responsibility.

## Acceptance Criteria
- GET `/users/me` (protected):
  - Requires valid JWT.
  - Returns the user's profile (id, email, firstName, lastName, isActive, createdAt, updatedAt, tenantId).
  - Excludes password hash.
  - Returns 200.
- PATCH `/users/me` (protected):
  - Requires valid JWT.
  - Accepts JSON with optional `firstName`, `lastName` (email and password changes may require separate endpoints; not included for simplicity).
  - Updates the user's record with provided fields.
  - Returns 200 with updated user profile (same shape as GET).
  - Returns 400 for invalid fields (e.g., trying to update email or password here).
  - Note: Email and password updates are out of scope for this task; they may be handled in separate endpoints if needed.
- User service methods:
  - `getUserById(userId)`: retrieves user (excluding password hash).
  - `updateUser(userId, data)`: validates and updates allowed fields.
- Unit and integration tests cover:
  - Successful retrieval and update.
  - Validation errors (invalid fields).
  - Unauthorized access.
  - Ensuring that a user cannot update another user's profile (by user ID manipulation – should not be possible as endpoint is `/me`).
  - That updating firstName and lastName persists.
  - That email and password cannot be updated via this endpoint (if attempted, returns 400).

## Files/Modules Likely to be Touched
- `src/modules/users/` (user service, repository, controller)
- `src/app/middleware/` (authentication middleware)
- `src/app/routes/users.ts` (routes for `/users/me`)

## Tests to Add or Update
- Integration tests using authenticated user:
  - Get profile after login.
  - Update firstName and lastName.
  - Attempt to update email (should 400).
  - Attempt to update password (should 400).
  - Attempt to access another user's profile via `/users/:id` (if such endpoint exists – not in contracts, so we assume it doesn't; but we should ensure no accidental exposure).
- Unit tests for user service update validation.

## Dependencies
- T-003: Authentication for protecting endpoints.
- T-002: User table exists.
- T-004: Tenant service (to get tenant info in user profile? Actually, user profile includes tenantId; we can fetch from user record directly. However, to return tenant details (name, etc.), we might need to join with tenant. The API contract for `/users/me` includes tenantId only, not tenant details. The contract shows:
  ```json
  {
    "id": "...",
    "email": "...",
    "firstName": "...",
    "lastName": "...",
    "isActive": true,
    "createdAt": "...",
    "updatedAt": "...",
    "tenantId": "..."
  }
  ```
  So we only need to return the tenantId from the user record. No join needed.
  However, T-004's GET `/users/me/tenant` returns the full tenant object. That endpoint will need to fetch the tenant by the user's tenant_id.
  So T-005 does not depend on T-004 for the user profile endpoint, but T-004's `/users/me/tenant` depends on the user's tenant_id.

## Out of Scope
- Updating email or password via this endpoint (consider separate endpoints if required).
- Deleting user account.
- Listing users (admin functionality).
- Role-based access control within tenant.
- Two-factor authentication setup.

## Important Implementation Notes
- The PATCH endpoint should only allow updating firstName and lastName as per the API contract. If we want to allow other fields later, we can extend.
- Validate that firstName and lastName are strings and within reasonable length.
- Use Prisma's update method with selective fields.
- Ensure that the user's tenantId is not updatable via this endpoint (it should be immutable after registration, except via tenant transfer – not required).
- Return the updated user with the same shape as GET (including tenantId).
- For security, never return the password hash in any user response.
