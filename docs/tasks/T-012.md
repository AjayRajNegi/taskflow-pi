# Task T-012: Security middleware: authentication, authorization, input validation

## Goal
Implement reusable middleware for authentication, authorization, and input validation to secure API endpoints.

## Requirements Covered
- From project requirements: Input validation, authentication and authorization handling.
- From security model: Authentication model, authorization model, input validation rules, logging rules.
- From system components: HTTP layer responsibility includes authentication middleware, authorization checks, input validation; Shared modules provide validation and authentication utilities.

## Acceptance Criteria
- Authentication middleware:
  - Verifies JWT token in `Authorization` header.
  - Extracts user ID, email, tenant ID from token payload.
  - Attaches user object to request (e.g., `req.user`).
  - Returns 401 if token missing, invalid, or expired.
  - Does not leak token details in logs or error messages.
- Authorization middleware (or integrated):
  - For tenant-owned resources, ensures that the resource's `tenant_id` matches the authenticated user's `tenant_id`.
  - Can be used as a separate middleware or included in service layer checks.
  - Returns 403 if user lacks permission for the action (though we often use 404 for tenant mismatch to avoid leaking existence).
  - Note: We may implement authorization checks in the service layer rather than middleware for flexibility; however, a middleware can enforce tenancy for routes that follow a pattern (e.g., `/tasks/:taskId`).
- Input validation middleware:
  - Uses Zod schemas to validate request body, query parameters, and path parameters.
  - Returns 400 with detailed error messages on validation failure.
  - Schemas are defined per endpoint and reused.
  - Does not log sensitive validation data (e.g., passwords).
- Shared validation module:
  - Provides reusable Zod schemas (e.g., UUID, email, password, tenantId).
  - Provides custom refinements (e.g., assignee belongs to same tenant).
- Shared authentication utilities:
  - JWT sign and verify functions.
  - Password hashing and comparison (bcrypt).
- Logging of security events:
  - Authentication failures (invalid token, expired token) logged at warn level.
  - Authorization failures (tenant mismatch) logged at warn level as potential security events.
  - Validation errors logged at debug level.

## Files/Modules Likely to be Touched
- `src/app/middleware/` (authentication.ts, authorization.ts, validation.ts)
- `src/shared/auth/` (JWT utilities, password hashing)
- `src/shared/validation/` (Zod schemas, custom refinements)
- `src/shared/tenancy/` (helpers for tenant context)
- `src/app/errors/` (custom error classes for formatting responses)
- `src/app/routes/` (routes will use the middleware)
- `src/shared/logging/` (logging utilities – ensure security events are logged appropriately)

## Out of Scope
- Role-based access control (RBAC) middleware – open question.
- Rate limiting middleware – covered in T-013.
- CSRF protection – not needed for API using Bearer tokens.
- Clickjacking, XSS protection – not relevant for API.
- HTTP headers like HSTS – handled by reverse proxy or server configuration.
- Input validation for file uploads (multipart) – handled separately in T-007.

## Important Implementation Notes
- Authentication middleware should:
  1. Extract token from `Authorization: Bearer <token>`.
  2. Verify signature and expiration using `jsonwebtoken` or similar.
  3. Fetch user from database by userId (from token) to ensure user exists and is active (optional but recommended).
  4. Attach `{ id, email, tenantId }` to request.
  5. If user not found or inactive, return 401.
- Authorization middleware for tenancy:
  - Option A: Create a middleware that loads the resource based on route parameters (e.g., taskId) and checks tenantId. This is route-specific and may be better as a decorator or service layer check.
  - Option B: Implement a helper function `assertTenantMatch(resourceTenantId, userTenantId)` used in services.
  - We'll implement both: a middleware for common patterns (like `/tasks/:taskId`) and encourage service layer checks for complex cases.
  - For routes that don't have a single resource ID (e.g., `/tasks` list), the authorization is handled in the service by filtering on tenantId.
- Input validation:
  - Use Zod to define schemas for each endpoint.
  - Create a middleware that validates `req.body`, `req.query`, `req.params` against the schema.
  - Format validation errors as `{ error: { code: 'VALIDATION_ERROR', message: '...' } }`.
  - Do not include field names in error messages if they could be sensitive? We'll include them for developer experience but ensure they don't leak sensitive data (e.g., not revealing password values).
- Logging:
  - Use structured logging (JSON).
  - Log authentication failures with user-provided email (if available from token) and reason.
  - Log authorization failures with userId, tenantId, and requested resource tenantId.
  - Ensure logs are stored securely and rotated.
- Error handling middleware:
  - Catch asynchronous errors in routes and convert to HTTP responses.
  - Convert application-specific errors (ValidationError, AuthenticationError, etc.) to appropriate status codes.
  - Ensure 500 errors do not leak stack traces.
