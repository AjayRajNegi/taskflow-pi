# Task T-006: Task service and API: task CRUD operations

## Goal
Implement the full CRUD API for tasks with pagination, filtering, and tenant isolation.

## Requirements Covered
- From project requirements: Task management API (create, read, update, delete tasks).
- From API contracts: `/tasks` (GET, POST), `/tasks/:taskId` (GET, PATCH, DELETE).
- From data model: Tasks table definition, relationships, constraints.
- From security model: Tenant-isolation model, authorization model.
- From system components: Task service responsibility.

## Acceptance Criteria
- GET `/tasks` (protected):
  - Requires valid JWT.
  - Supports query parameters: `page` (default 1), `limit` (default 10, max 100), `status` (optional), `assigneeId` (optional UUID).
  - Returns paginated list of tasks belonging to the authenticated user's tenant.
  - Response includes `data` array and `pagination` object.
  - Tasks are filtered by the user's tenant_id.
  - Status filter validates against allowed values: 'todo', 'in_progress', 'done'.
  - AssigneeId filter ensures the assignee exists and is in the same tenant (if provided).
  - Returns 200 even if no tasks match.
  - Returns 400 for invalid query parameters (e.g., page < 1, limit > 100).
- POST `/tasks` (protected):
  - Requires valid JWT.
  - Accepts JSON with `title` (required), `description` (optional), `status` (optional, default 'todo'), `assigneeId` (optional UUID).
  - Creates a task in the authenticated user's tenant.
  - Validates that assigneeId (if provided) is a user in the same tenant.
  - Returns 201 with the created task.
  - Returns 400 for validation errors (missing title, invalid status, invalid assignee).
  - Publishes a `task.assigned` event if assigneeId is set (to trigger notification job).
- GET `/tasks/:taskId` (protected):
  - Requires valid JWT.
  - Returns the task if it exists and belongs to the user's tenant.
  - Returns 200.
  - Returns 404 if task not found or not accessible (to avoid leaking existence).
- PATCH `/tasks/:taskId` (protected):
  - Requires valid JWT.
  - Accepts partial JSON with `title`, `description`, `status`, `assigneeId`.
  - Updates the task if it belongs to the user's tenant.
  - Validates assigneeId (if provided) is a user in the same tenant.
  - Returns 200 with updated task.
  - Returns 400 for validation errors.
  - Returns 404 if task not found or not accessible.
  - Publishes `task.assigned` event if assigneeId is set or changed to a new user.
- DELETE `/tasks/:taskId` (protected):
  - Requires valid JWT.
  - Deletes the task if it belongs to the user's tenant.
  - Returns 204 on success.
  - Returns 404 if task not found or not accessible.
- Task service methods:
  - `createTask(data, userId)`: validates, sets tenantId from user, creates task, publishes event.
  - `getTask(taskId, userId)`: retrieves task with tenant check.
  - `updateTask(taskId, data, userId)`: validates, updates with tenant check.
  - `deleteTask(taskId, userId)`: deletes with tenant check.
  - `getTasks(filter, pagination, userId)`: lists tasks with tenant filter.

## Important Implementation Notes
- Tenant isolation is critical: every task query must include `WHERE tenant_id = ?` using the authenticated user's tenant_id.
- For assignee validation: when creating/updating a task with assigneeId, verify that the user exists and that user.tenant_id matches the task's tenant_id (which is the same as the authenticated user's tenant_id).
- The `task.assigned` event should be published after the task is successfully created/updated. The event payload should include at least taskId, assigneeId, and optionally task title.
- Use Prisma's transaction if needed for creating task and publishing event reliably? However, event publishing is external (to BullMQ) and should not be in the same transaction. We'll use an outbox pattern or simply publish after commit; if publishing fails, we may have a retry mechanism (but the notification job will handle retries via BullMQ). For simplicity, we can publish after the Prisma transaction; if it fails, we log and may rely on the notification job to retry? Actually, the notification job is triggered by the event; if the event fails to publish, the job won't run. We'll need to ensure event publishing is reliable. We can use the application service to publish after the transaction succeeds, and if publishing fails, we log and optionally store a failed event for retry (but that's more complex). For V1, we'll assume that publishing to BullMQ is reliable (if Redis is up). We'll add error logging and consider it a best-effort; if it fails, the task is still created but notification may not be sent. We can improve later with an outbox table.
- Pagination: use Prisma's `skip` and `take`. Calculate total items with `count`.
- Status field: store as string, validate against allowed values in service layer.
- Title: required, non-empty string with reasonable max length (e.g., 255).
- Description: optional, can be long text.
- Timestamps: managed by Prisma.
