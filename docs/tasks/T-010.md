# Task T-010: Background job setup for task assignment notifications

## Goal
Implement background job processing for sending email notifications when a task is assigned to a user.

## Requirements Covered
- From project requirements: Background notifications for task assignment.
- From architecture: Background jobs use BullMQ + Redis.
- From system components: Notification service responsibility; Job queue and Worker process.
- From security model: Background-job security, input validation rules.

## Acceptance Criteria
- When a task is created or updated with an assigneeId (and the assignee is different from previous), a notification job is added to the BullMQ queue.
- The job payload contains minimal data: taskId, assigneeUserId (or user email/name), and optionally task title.
- A worker process runs that listens to the queue, processes jobs by:
  - Retrieving task and user data via services (with tenant checks).
  - Sending an email via the Notification Service (which uses Email Provider abstraction).
  - Logging success or failure.
- The job is designed to be idempotent: sending the same notification multiple times should not cause issues (though may be annoying; we accept that for V1).
- Retry configuration: jobs are retried up to 3 times with exponential backoff before moving to failed set.
- Failed jobs are logged and can be inspected for manual retry.
- Unit and integration tests cover:
  - Job is queued when task is assigned.
  - Job payload contains expected data.
  - Worker processes job and attempts to send email.
  - Email sending is mocked; we verify that the email provider's send method is called with correct parameters.
  - Job retry logic works (simulate failure).
  - Failed job ends up in the failed set after max retries.
  - Tenant isolation: worker verifies that the task and user belong to the same tenant before sending email.
  - If task or user is deleted before job runs, job handles gracefully (logs and marks as completed or failed? We'll log and consider it done, as the entity no longer exists).
- Notification service methods:
  - `sendNotification(userId, taskId, emailOptions)`: constructs email and sends via provider.
  - `processNotificationJob(job)`: called by worker.
- Email provider abstraction:
  - Interface: `send(options: SendEmailOptions): Promise<void>`
  - Implementation: e.g., SES, SendGrid, or SMTP (configurable).
- Configuration: BullMQ queue name, Redis connection, job retry settings.

## Out of Scope
- Notification templates beyond basic text (we'll send a simple email with task details).
- Email delivery guarantees or tracking (opens, clicks).
- Unsubscription links.
- Notification preferences per user.
- Other notification types (e.g., task completion, comments).
- In-app notifications.
- Rate limiting on email sending.
- Using a different queue system (e.g., Amazon SQS) – we're using BullMQ+Redis as per architecture.
- Storing notification history (sent status) – open question; we may not store it beyond job completion.

## Important Implementation Notes
- The task service, upon creating or updating a task with assigneeId, should publish a domain event (e.g., `task.assigned`) that the notification service listens to, or directly add a job to the queue. We'll use the service to add job directly for simplicity, but we can also use an event-driven approach. Given the system components, the notification service subscribes to `task.assigned` event. We'll have the task service publish an event (via an event emitter) and the notification service consume it to enqueue the job. This decouples the task service from the queue.
- However, to keep it simple for V1, we can have the task service directly add a job to the notification queue when assignee is set. We'll note that the notification service is responsible for the job processing.
- The job payload should include: `taskId`, `assigneeUserId`. The worker will then fetch the task and user to get details for the email.
- Email content: include task title, assignee name, and a link to the task (if we had a UI; but since API-only, we may just mention the task ID). We'll keep it simple: "You have been assigned to task: [task title] (ID: [taskId])".
- The email provider abstraction allows swapping implementations; we'll implement a dummy provider for testing that logs the email.
- Configuration: set `QUEUE_NAME_NOTIFICATIONS` to `task-notifications`.
- Worker process: we'll have a separate `src/worker.ts` that initializes the workers for notification and payment retry jobs.
- Ensure the worker can be started independently of the API server (same codebase).
- Use BullMQ's built-in retry mechanisms: `attempts`, `backoff` configuration.
- When a job fails repeatedly, it moves to the failed set; we should have a way to retry failed jobs manually (e.g., via a CLI script).
- Log job processing attempts and outcomes.
- Do not store sensitive data in job payload (e.g., password, token).
