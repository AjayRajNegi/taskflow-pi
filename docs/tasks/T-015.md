# Task T-015: Testing setup: unit and integration tests for core functionality

## Goal
Establish a comprehensive testing framework to unit test business logic and integration test API endpoints, ensuring correctness and preventing regressions.

## Requirements Covered
- From project requirements: Testing requirements (multi-tenancy, API, background jobs, payments).
- From architecture: Testing architecture (unit, integration, API tests).
- From system components: All components should be testable in isolation.
- From security model: Security-critical behavior has automated tests.

## Acceptance Criteria
- Testing framework:
  - Uses Vitest as the test runner (compatible with Bun).
  - Supports TypeScript natively.
  - Configured for unit tests (mocking dependencies) and integration tests (real database, Redis, etc.).
  - Test files are colocated with source or in a `__tests__` directory; we'll colocate for simplicity.
  - Test coverage is tracked (optional but encouraged).
- Unit tests:
  - Test individual functions in services, repositories, and utilities.
  - Mock external dependencies (database, email provider, payment provider, storage).
  - Test validation logic, error handling, and business rules.
  - Run quickly and in isolation.
- Integration tests:
  - Test API endpoints with a real test database and Redis instance.
  - Test end-to-end flows: user registration, login, task creation, file upload, etc.
  - Test multi-tenancy isolation: verify that users cannot access data from other tenants.
  - Test background job processing: enqueue a job and verify it processes correctly.
  - Test webhook handling with simulated payment provider events.
  - Test error cases: validation errors, authentication failures, etc.
  - Use transactions or rollback to isolate test data.
- Test organization:
  - `__tests__` folders within each module (e.g., `src/modules/tasks/__tests__/task.service.test.ts`).
  - API test files in `src/__tests__/api/` or similar.
  - Setup and teardown scripts for test databases.
- Test data factories:
  - Functions to generate test tenants, users, tasks, etc.
  - Avoid hardcoded IDs; use generated UUIDs.
- Continuous Integration:
  - Test suite runs on push and pull requests.
  - Fails if any test fails.
  - Linting and type checking are part of the CI pipeline (but not in this task).
- Acceptance criteria for the task:
  - A basic unit test passes (e.g., utility function).
  - An integration test passes (e.g., can register and login a user).
  - The test suite can be run with `bun test` or similar.
  - Test reports are generated (optional).

## Files/Modules Likely to be Touched
- `vitest.config.ts` (Vitest configuration)
- `src/shared/test/` (test helpers, factories, database setup)
- `src/modules/__tests__/` (unit tests for each module)
- `src/__tests__/api/` (integration tests for API endpoints)
- `src/__tests__/jobs/` (tests for background job processing)
- `package.json` (test script)
- Environment variables for testing: `TEST_DATABASE_URL`, `TEST_REDIS_URL`

## Tests to Add or Update
- Write tests for:
  - User service: create, authenticate, update.
  - Tenant service: create, get user's tenant.
  - Task service: CRUD with tenant isolation.
  - File service: upload, metadata, delete with storage mock.
  - Payment service: subscription creation (mock provider), webhook handling.
  - Notification service: job processing (mock email provider).
  - Middleware: authentication, validation, rate limiting.
  - Utilities: JWT, password hashing, validation schemas.
  - API endpoints: full flow tests.
- Ensure that tests clean up after themselves (e.g., delete test data).
- Use a separate test database to avoid interfering with development data.

## Dependencies
- T-001: Project setup must include Vitest and testing dependencies.
- T-002: Database schema must exist for integration tests to run.
- T-003: Authentication is needed for many integration tests.
- T-004 through T-014: Each component's functionality will be tested.

## Out of Scope
- End-to-end tests involving external services (email, payment provider, storage) – we will mock or use test doubles for these in unit and integration tests. However, integration tests may use a local file storage adapter and a fake email provider that logs to console.
- Performance testing (load, stress) – out of scope for V1.
- Security penetration testing – out of scope (though we write security tests).
- UI tests – out of scope (no web UI).
- Mobile app tests – out of scope.
- Contract testing with third-party services (e.g., Razorpay) – we mock them.

## Important Implementation Notes
- Test database:
  - Use a separate PostgreSQL database for testing (e.g., `taskflow_test`).
  - Run migrations against this database before each test suite.
  - Optionally use transactions and rollback after each test for speed.
  - Alternatively, drop and recreate schema between tests (slower but cleaner).
- Redis for testing:
  - Use a separate Redis database (e.g., DB 1) or flushdb between tests.
  - For BullMQ tests, we may need to ensure queues are clean.
- Mocking:
  - Use Vitest's mocking capabilities or libraries like `ts-mockito` or `jest-extended` (but Vitest has Jest-like mocking).
  - Mock external services: email provider, payment provider (Razorpay), storage adapter.
  - Verify that mocks are called with expected arguments.
- Test data factories:
  - Create functions like `makeTestTenant()`, `makeTestUser(overrides)`, `makeTestTask(overrides)`.
  - Use UUID v4 for IDs.
  - Avoid using real email domains; use `example.com` or similar.
- API tests:
  - Use a library like `supertest` if the framework supports it, or make HTTP requests directly to the test server.
  - Start the server in test mode on a random port.
  - Authenticate via login to get token for protected requests.
  - Assert on response status, headers, and body.
- Background job tests:
  - Enqueue a job and then call the worker processor directly (or use BullMQ's test helpers).
  - Mock the email provider and verify that `send` is called.
  - Test retry logic by simulating failures.
- Payment webhook tests:
  - Generate a valid Razorpay webhook signature for a test payload.
  - Post to the webhook endpoint and verify subscription updates.
- Use `beforeAll`, `afterAll`, `beforeEach`, `afterEach` hooks appropriately.
- Ensure tests are deterministic and do not rely on external state.
- Run tests with `--detect-open-handles` to avoid hanging processes.
- In CI, consider using services like PostgreSQL and Redis via Docker Compose or GitHub Actions services.
