# Task T-014: Logging and monitoring setup

## Goal
Configure structured logging and basic monitoring for the application to support observability and debugging.

## Requirements Covered
- From project requirements: Observability, logging to diagnose failures.
- From architecture: Observability requirements, logging rules.
- From security model: Logging rules (never log secrets, avoid unnecessary PII).
- From system components: Shared modules provide logging utilities.

## Acceptance Criteria
- Logging configuration:
  - Uses structured JSON format for log entries.
  - Includes timestamp, level, message, and optional metadata (requestId, userId, tenantId, etc.).
  - Log level is configurable via environment variable (e.g., `LOG_LEVEL=info`).
  - Does not log sensitive data: passwords, tokens, API keys, payment details, file contents.
  - Logs authentication failures (with email from token, if available), authorization failures, validation errors, and unexpected errors.
  - Logs outgoing HTTP requests to external services (email, payment, storage) at debug level.
  - Logs incoming requests at info level (method, path, status, response time).
  - Logs background job processing attempts and outcomes.
- Request ID correlation:
  - Generates a unique request ID for each incoming request.
  - Includes request ID in all logs related to that request.
  - Passes request ID to downstream services (if applicable) via headers or context.
- Monitoring:
  - Basic health check endpoint (already in T-001) serves as a liveness probe.
  - Readiness probe may be added (checks database and Redis connectivity).
  - Metrics collection is out of scope for V1 (may be added later).
  - Error rates and latency can be inferred from logs.
- Unit and integration tests cover:
  - Log entries are JSON and parsable.
  - Sensitive data is not present in logs (test by attempting to log a password and verifying it's not there).
  - Request ID is included in logs.
  - Log levels respect configuration (e.g., debug logs only appear when level is debug).
  - Error logs contain stack traces only in development (not in production).
- Files to demonstrate logging:
  - `src/shared/logging/` (logger utility)
  - `src/app/middleware/logging.ts` (request logging middleware)
  - `src/app/errors/` (error handling middleware that logs errors)
  - `src/modules/` (services log important operations)

## Tests to Add or Update
- Integration tests that:
  - Capture logs during test execution and verify structure.
  - Verify that logging a user's password does not appear in logs.
  - Verify that authentication failure logs include the attempted email (from request) but not password.
  - Verify that authorization failure logs include userId and tenantIds involved.
  - Verify that request ID is consistent across logs for a single request.
- Unit tests for logging utility:
  - Test that logging methods produce valid JSON.
  - Test that masking function works for sensitive strings.

## Dependencies
- T-001: Project setup must include a logging library (e.g., pino, winston, or bunyan) compatible with Bun.
- T-003: Authentication will log failures.
- T-006: Task operations will log important events.
- T-007: File upload will log validation errors.
- T-008, T-009: Payment operations will log failures.
- T-010: Background jobs will log processing attempts.

## Out of Scope
- Distributed tracing (e.g., Jaeger, Zipkin).
- Advanced metrics (Prometheus counters, histograms).
- Log aggregation and storage solutions (ELK stack).
- Real-time alerting based on logs.
- Audit logs for compliance (beyond basic security events).
- Logging of performance metrics (CPU, memory) – may be collected separately.
- Logging to syslog or journalctl – we'll log to stdout/stderr for container environments.

## Important Implementation Notes
- Choose a logging library that supports JSON output and is performant (e.g., Pino is popular for Node.js/Bun).
- Create a logger instance that is shared across the application.
- Middleware for request logging:
  - Generate request ID (e.g., using `uuid()` or `nanoid()`).
  - Log incoming request: method, path, query string length, user agent (optional), IP address.
  - Log outgoing response: status code, response time.
  - In case of error, log error details.
- Error handling middleware:
  - Catch errors, log them with stack trace (in development) or without (in production).
  - Convert to appropriate HTTP response.
  - Ensure that the error logged does not contain sensitive data (e.g., if error is from payment provider, do not log full API key).
- When logging external service calls, log only metadata (e.g., "Calling Razorpay API: subscription.create") and not the full payload or secrets.
- For authentication failures, log the email provided in the request (if available) but not the password.
- For authorization failures, log the user ID from token, the tenant ID from token, and the tenant ID of the resource being accessed.
- Ensure that logs are flushed appropriately and do not buffer excessively.
- In test environment, we may redirect logs to a test sink or disable logging to keep test output clean.
- Consider log rotation if logging to files (but in containerized environments, stdout/stderr is handled by orchestrator).
