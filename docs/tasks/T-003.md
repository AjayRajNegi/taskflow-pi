# Task T-003: Authentication: user registration and login endpoints

## Goal
Implement user registration and login endpoints with JWT-based authentication, password hashing, and tenant association during registration.

## Requirements Covered
- From project requirements: Multi-tenancy, users must belong to a tenant.
- From API contracts: `/auth/register` and `/auth/login` endpoints.
- From security model: Authentication model (JWT), password hashing, validation rules.
- From system components: User service responsibility includes authentication; HTTP layer handles authentication middleware.

## Acceptance Criteria
- POST `/auth/register`:
  - Accepts JSON with `email`, `password`, `firstName`, `lastName`, `tenantId`.
  - Validates input (email format, password min length 8, tenantId UUID, tenant exists).
  - Hashes password using bcrypt (cost factor 12).
  - Creates user record with provided `tenantId`.
  - Returns 201 with user info (excluding password hash).
  - Returns 400 for validation errors, 409 for duplicate email, 404 if tenant not found.
- POST `/auth/login`:
  - Accepts JSON with `email` and `password`.
  - Validates input.
  - Finds user by email, verifies password hash.
  - On success, returns JWT token (signed with secret) and user info (excluding password hash).
  - Returns 401 for invalid credentials.
- JWT middleware:
  - Validates token on protected routes.
  - Extracts user ID, email, tenant ID from token payload.
  - Attaches user context to request for downstream use.
- Password hashing is never logged or exposed.
- Unit and integration tests cover:
  - Successful registration and login.
  - Validation errors.
  - Duplicate email.
  - Non-existent tenant during registration.
  - Invalid login credentials.
  - Token validation and user context propagation.

## Important Implementation Notes
- Registration must verify that the provided `tenantId` exists in the tenants table (to prevent creating users for non-existent tenants).
- The user's `tenant_id` is set from the `tenantId` in registration request.
- Login does not require tenantId; it is derived from the user record.
- JWT payload should include: `userId`, `email`, `tenantId`, `iat`, `exp`.
- Use HTTP-only cookies? The API contracts specify Bearer token in Authorization header, so we'll use header.
- Token expiration: set to a reasonable value (e.g., 1 hour).
- Ensure the authentication middleware is applied to all protected routes (except auth and health).
- Handle token expiration gracefully (return 401).
- Use a shared validation module for Zod schemas to avoid duplication.
- Log authentication failures (without passwords) for security monitoring.
