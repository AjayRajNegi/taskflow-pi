# Task T-008: Subscription service and API: get subscription status, create subscription

## Goal
Implement subscription management for tenants, including retrieving subscription status and creating a subscription (initiating payment).

## Requirements Covered
- From project requirements: Payment support for premium features.
- From API contracts: `/users/me/tenant/subscription` (GET, POST).
- From data model: Subscriptions table definition, relationships, constraints.
- From security model: Payment/webhook security, tenant-isolation model.
- From system components: Payment service responsibility.

## Acceptance Criteria
- GET `/users/me/tenant/subscription` (protected):
  - Requires valid JWT.
  - Returns the subscription for the authenticated user's tenant.
  - Returns 200 with subscription info (id, status, planId, currentPeriodEnd, timestamps).
  - Returns 404 if no subscription exists (tenant is on free tier).
- POST `/users/me/tenant/subscription` (protected):
  - Requires valid JWT.
  - Accepts JSON with `planId` (required), `paymentMethodId` (optional).
  - Initiates subscription creation for the authenticated user's tenant.
  - Returns 201 with subscription info (may include clientSecret for payment confirmation).
  - Returns 400 if planId missing.
  - Returns 402 if payment fails (optional; or 500).
  - Returns 503 if payment provider is unavailable.
  - Note: The exact flow (redirect vs SDK) is an open question; we'll assume the API returns necessary data for client-side completion.
- Subscription service methods:
  - `getSubscriptionByTenantId(tenantId)`: retrieves subscription.
  - `createSubscription(tenantId, planId, paymentMethodId)`: validates, creates subscription record, interacts with payment provider.
- Payment service methods (if separate):
  - `createOrder(planId, paymentMethodId)`: interacts with Razorpay to create subscription/order.
  - `verifyPayment(...)`: not needed if webhook handles confirmation.
- Unit and integration tests cover:
  - Successful subscription retrieval (when exists).
  - Successful subscription creation (mock payment provider).
  - Handling of no subscription (404).
  - Validation errors.
  - Unauthorized access.
  - Tenant isolation: user cannot view or create subscription for another tenant.
  - Idempotency: creating subscription for a tenant that already has one may return existing or error (open question; we'll assume it updates or returns 409).
  - Payment provider failure handling.

## Out of Scope
- Subscription updates (changing plan, canceling) – not in API contracts.
- Subscription renewal handling (webhook will update status).
- Invoice retrieval.
- Payment history or receipts.
- Fraud detection.
- Multiple payment methods.
- Customer portal.
- Detailed payment flow: we are not implementing the client-side Razorpay SDK integration; we assume the API returns data needed for the client to complete payment (e.g., order ID, amount, etc.). The exact response structure is an open question.
- Webhook endpoint for payment provider (covered in T-009).

## Important Implementation Notes
- The create subscription endpoint should:
  1. Get the tenantId from the authenticated user.
  2. Validate that the tenant exists and is active.
  3. Check if a subscription already exists for the tenant (based on business rules: maybe allow only one, or allow updating? We'll assume one subscription per tenant; if exists, return 409 or update? Open question. For now, we'll allow creating a new subscription only if none exists; if exists, return 409 Conflict.)
  4. Call payment service to create a subscription/order with Razorpay.
  5. Save the subscription record with initial status (e.g., 'created' or 'pending') awaiting payment confirmation via webhook.
  6. Return subscription info and any client-side data needed (e.g., orderId, amount, currency).
- The webhook (T-009) will update the subscription status upon payment confirmation.
- We must store the Razorpay subscription ID in our subscription record for future reference.
- PlanId should be validated against a list of allowed plans (could be hardcoded or fetched from config; open question).
- PaymentMethodId is optional; if not provided, the client may need to use Razorpay SDK to collect payment details.
- Use Prisma transactions to ensure subscription record creation is atomic.
- Handle payment provider errors gracefully and return appropriate HTTP status.
- Log payment attempts (without sensitive data) for audit.
- Ensure that subscription creation is idempotent with respect to payment provider (we'll rely on Razorpay's idempotency key or our own).
