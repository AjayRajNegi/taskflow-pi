# Task T-011: OpenAPI specification generation and validation

## Goal
Generate and validate the OpenAPI specification from the implemented API endpoints to ensure documentation accuracy.

## Requirements Covered
- From project requirements: OpenAPI specification must exist and match the API.
- From architecture: OpenAPI is required; preferred approach is to generate from implementation.
- From system components: HTTP layer responsibility includes OpenAPI integration.

## Acceptance Criteria
- OpenAPI specification (JSON or YAML) is generated and available at `/api/docs` or similar endpoint (or generated as a file).
- The specification accurately documents all implemented endpoints:
  - Authentication: `/auth/register`, `/auth/login`
  - Tenant: `/tenants`, `/users/me/tenant`
  - User: `/users/me`
  - Tasks: `/tasks` (GET, POST), `/tasks/:taskId` (GET, PATCH, DELETE)
  - Attachments: `/tasks/:taskId/attachments` (POST), `/attachments/:attachmentId` (GET, DELETE)
  - Subscription: `/users/me/tenant/subscription` (GET, POST)
  - Payment webhook: `/payments/webhook` (POST)
  - Health check: `/health`
- Each endpoint includes:
  - HTTP method and path.
  - Summary and description.
  - Parameters (path, query, header).
  - Request body schema (if applicable).
  - Response schemas for success and error responses.
  - Authentication requirements (Bearer token where needed).
- The specification is validated as part of the CI/build process (e.g., using a validator like `swagger-cli validate`).
- Generated specification matches the contracts in `docs/api-contracts.md` (we can compare manually or via tool).
- Unit tests may include a snapshot test to ensure the spec does not change unexpectedly.

## Files/Modules Likely to be Touched
- `src/app/routes/` (routes files – will be scanned for OpenAPI annotations)
- `shared/openapi/` (decorators or helpers for generating spec, if using annotation-based approach)
- `src/app/openapi.ts` (spec generation script or setup)
- Configuration: `OPENAPI_ENABLED`, `OPENAPI_PATH`
- Dependencies: `swagger-ui-express`, `ts-json-schema-generator`, or similar, or use JSDoc annotations with a library like `tsoa`.
- Alternatively, if the chosen HTTP framework supports OpenAPI natively (e.g., via decorators), we'll use that.
- Given the architecture says "TypeScript/Bun-compatible HTTP framework", we'll assume we can choose one that supports OpenAPI generation (e.g., Tsoa, NestJS, but note NestJS may be heavy; we'll pick a lightweight one).

## Tests to Add or Update
- Test that the OpenAPI endpoint returns valid JSON/YAML.
- Test that the spec includes all expected routes.
- Test that the spec matches a baseline (snapshot test).
- In CI, fail if spec validation fails.

## Dependencies
- T-003, T-004, T-005, T-006, T-007, T-008, T-009: All API routes must be implemented to generate a complete spec.
- T-001: Project setup must include necessary dependencies for OpenAPI generation.

## Out of Scope
- Designing the OpenAPI specification manually (we are generating from code).
- Hosting the spec on a separate portal (we'll serve it locally).
- Generating client SDKs from the spec (out of scope for V1).
- Detailed examples in the spec beyond basic schemas (we'll add examples where practical).
- Versioning the OpenAPI spec separately from API version (we'll include version in info).

## Important Implementation Notes
- Choose an HTTP framework that supports OpenAPI generation via decorators or automatic route scanning (e.g., Tsoa). If the framework does not, we may need to annotate routes manually or use a separate tool that analyzes the routes.
- Since we are not writing actual code, we note that the implementation team should select a compatible approach.
- The spec should include security schemes for Bearer token.
- Error responses should follow the standard format defined in API contracts.
- For multipart endpoints (file upload), the spec should reflect `multipart/form-data`.
- The spec should be served at a path like `/api/docs` with Swagger UI for easy viewing.
- Ensure that the spec generation does not include internal routes (e.g., internal admin routes not exposed).
- Set `openapi: 3.0.0` or `3.0.3`.
- Include API version in the info object (e.g., `version: '1.0.0'`).
- If generating as a file, also output to `docs/openapi.yaml` for version control.
- In test environment, we may skip spec generation to speed up tests.
